# Comparisons

habit answers one question: which modules does this host import? Other
frameworks answer it differently, or answer a wider question. This page
compares habit with four of them. Each claim about another project was checked
against its source at the revision named in its section; file paths are
relative to that repository. habit is described from this repository's code.

## Summary

| | group member off, before import | back on, downstream | unselected files never imported | resolved inventory | name clash across sources | darwin | standalone Home Manager | directory discovery |
|---|---|---|---|---|---|---|---|---|
| **habit** | yes: `enable = false` beats the group's `mkDefault` | yes: ordinary priorities (`mkForce`) | yes, tested; override records are read on every host | yes: names, providers, source paths | error, naming every source | no | no | no: the registry is written (or generated) by the consumer |
| **den** | yes: `excludes` | no: `excludes` merges by list concatenation | excluded aspects are not applied | `entity.aspects`: identities, no source paths | same name merges | yes | yes: `den.homes` | not in core |
| **dendritic + flake-parts** | no: a group is a module whose `imports` is a plain list | n/a | n/a: a module is imported wherever a list names it | no | same name merges | yes: classes are free-form | yes: a `homeManager` class | a convention (import-tree), not required |
| **snowfall-lib** | no: every module in `modules/nixos` is in every NixOS system | n/a | no | no | n/a: names are paths in one tree | yes | yes: `homes/` | yes |
| **blueprint** | no: no groups | n/a | n/a: a host imports what it names | no | n/a: names are paths in one tree | yes | yes: `homeConfigurations."user@host"` | yes |

Where the others win, plainly:

- **den** builds darwin hosts and standalone Home Manager homes, and routes
  configuration between entities (hosts, users, homes) in general. habit does
  none of these: it builds NixOS hosts, with Home Manager as the NixOS module.
- **snowfall-lib** and **blueprint** discover hosts, modules and homes from
  the directory layout with no registry to write. habit's registry is written
  by hand or generated by the consumer.
- **flake-parts** has an ecosystem of modules to import and is a general flake
  framework. habit is one library function with no flake framework under it.

## den

Checked at vic/den `7594405`.

den's content unit is the aspect, declared under `den.aspects.<name>`: an
attrset whose class keys (`nixos`, `darwin`, `homeManager`) emit modules into
entities of that class. Hosts, users and homes are entities. Aspects pull
others in with `includes` and remove them from a subtree with `excludes`;
policies and `provides` route configuration across entities
(`AGENTS.md`, "Core concepts"; `docs/src/content/docs/reference/aspects.mdx`).

| question | den | habit |
| -------- | --- | ----- |
| remove a group member for one host | `excludes = [ den.aspects.kitty ]` on the host's aspect | `dendrites.kitty.enable = false` in the host record |
| how removal merges | `excludes` merges as `acc ++ …`, list concatenation (`modules/options.nix`) | a boolean merged by priority: a later layer can turn it back on with `mkForce` |
| what a host resolved | `entity.aspects`: resolved aspects with `.identity`, `.identityKey`, `.isNamed`; anonymous aspects are listed (`docs/src/content/docs/explanation/structural-introspection.mdx`) | `inventory`: groups, capabilities with provider and source path, users, matched records |
| one name defined in two files | `den.aspects` is a submodule with a freeform `lazyAttrsOf` (`nix/lib/aspects/types.nix`, `aspectsType`), so the definitions merge | a catalogue is an attrset; across sources `mergeRegistries` throws naming both |
| darwin | `den.classes` registers `darwin`; a darwin-system host becomes a `darwinConfigurations` entry (`modules/options.nix`; `docs/src/content/docs/guides/declare-hosts.mdx`) | not built; a `darwin` lane is accepted and never read |
| standalone Home Manager | `den.homes.<system>.<name>` (`docs/src/content/docs/guides/standalone-home-manager.mdx`) | not built |
| flake-parts | optional: `modules/outputs.nix` branches on its presence; `templates/minimal/flake.nix` uses plain `evalModules` | not used |

Choose den when you want parametric aspects (functions of `{ host, user }`,
`README.md`),
cross-entity routing, darwin or standalone homes. Choose habit when you want
membership settled by ordinary priorities, an inventory that names the file
behind each capability, and a merge that refuses a duplicate name.

## dendritic and flake-parts

Checked at mightyiam/dendritic `6c76240` and hercules-ci/flake-parts `024633c`.

The dendritic pattern makes every file a module of one top-level
configuration and stores lower-level modules (NixOS, Home Manager, darwin) as
option values in it. That configuration is "commonly" flake-parts, "but it
does not have to be" (`README.md`). flake-parts provides the option for it,
`flake.modules`, typed `lazyAttrsOf (lazyAttrsOf deferredModule)` and keyed by
class, then name (`extras/modules.nix`).

| question | dendritic + `flake.modules` | habit |
| -------- | --------------------------- | ----- |
| a group | a module whose `imports` lists others | an aggregation body: data naming members |
| remove a member for one host | `imports` is a plain list in the module system, with no priority; `disabledModules` removes a module by path or `key` from the collected result | `enable = false` beats the group's `mkDefault` before anything is imported |
| one name defined in two files | merges: `deferredModule` values merge under one name, which the pattern advertises ("Lower-level module merging", `README.md`) | across sources, an error |
| darwin, Home Manager | classes are free-form names, so their modules are published the same way | NixOS and the Home Manager NixOS module only |
| ecosystem | flake-parts: "an ecosystem of modules that you can import" (`README.md`) | none; one library |

In nixpkgs `e554fab` (this repository's pin), `lib/modules.nix`
`collectStructuredModules` loads every module and its `imports` and gathers each
`disabledModules` entry on the way; `filterModules` removes the disabled modules
only afterwards. A module named in `disabledModules` has been loaded by then,
and the `disabledModules` of what it imports are still collected.
`disabledModules` patches the result; it is not a selection layer.

habit does not replace flake-parts: a flake-parts flake can call
`mkNixosHost` like any other flake.

## snowfall-lib

Checked at snowfallorg/lib `6ee3542`.

snowfall-lib turns a directory layout into flake outputs: `systems/`,
`homes/`, `modules/nixos`, `modules/darwin` and more, read with `readDir`
(`snowfall-lib/fs/default.nix`). It builds on flake-utils-plus (`flake.nix`).

Every module under `modules/nixos` is placed in every NixOS system's module
list: `create-systems` takes `builtins.attrValues user-modules` into each
system's `modules` (`snowfall-lib/system/default.nix`). Whether a module does
anything on a given host is the module's own business, typically an option and
`mkIf`, which is the import-everywhere shape [the two passes](two-passes.md)
exist to avoid. In exchange, snowfall-lib needs no registry: a new directory is
a new host, home or module. It builds darwin systems (`modules/darwin`, the
darwin branch of `snowfall-lib/system/default.nix`) and standalone homes
(`homeConfigurations`, `snowfall-lib/home/default.nix`).

## blueprint

Checked at numtide/blueprint `8be7524`.

blueprint maps folders to flake outputs one to one: `hosts/` to
`nixosConfigurations` and `darwinConfigurations`, `modules/` to `nixosModules`
and `darwinModules` (`README.md`), discovered with `readDir` (`lib/default.nix`).
A user under `hosts/<host>/users/<user>` also becomes a standalone
`homeConfigurations."<user>@<host>"` (`lib/default.nix`). It does not build on
flake-parts; its README lists it as a related project.

blueprint has no notion of groups or selection: a host's configuration imports
the modules it names. That is the plain module system, and it is simple. habit
is for when the same groups are shared across hosts and a host needs to take a
group minus a member, with a record of what each host resolved.
